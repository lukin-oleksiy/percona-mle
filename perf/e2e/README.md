# End to end: an application against the same logic in MLE

`e2e.py` measures what an application sees: the time per request and the requests per second when the
logic runs in the client (Java or Python, with the round trips the logic needs) and when it runs in a
stored procedure (one `CALL`). The procedures and the clients contain the same logic; every variant
must pick the same ids (the run checks it).

## What it measures

Data: `items`, 100,000 × `VECTOR(768)` (clustered, normalised) with category, price and stock, an HNSW
index (cosine); 10,000 users with 20 viewed items each; promotions on 10 % of the items; 200 query
vectors. Made once by `setup.sql` (the same generator and seeds as the experiment of 16–18 Nov).

| case | what one request does |
|---|---|
| `chatty` | a user's profile and history → 200 HNSW candidates near the history's mean, scored → promotions of the shortlist → top 10 (an application: 3 dependent round trips) |
| `mmr500` | 500 HNSW candidates with their vectors, re-ranked by maximal marginal relevance |
| `rescore1000` | 1,000 HNSW candidates, rescored (similarity, price, stock, category) |
| `bulk` | all ~5,000 vectors of a category: centroid, the 10 most typical and the 10 outliers |
| `wb200`, `wb1000` | write-back: read 200 / 1,000 rows of a category with vectors, score them, upsert the scores in one transaction (an application: read, write, commit) |
| `wbvec200` | write-back of 200 rows with a new `VECTOR(768)` each |

| client | variant | where the logic runs |
|---|---|---|
| java | `app` | the Java client (Connector/J; `rewriteBatchedStatements` for the write-back) |
| java | `jvm` | `LANGUAGE JAVA` procedure, JVM worker (the same `Rerank.java`, as a library) |
| python | `app` | the Python client (mysql-connector-python, numpy) |
| python | `jvm` | `LANGUAGE PYTHON` procedure: GraalPy in the JVM worker |
| python | `cpython` | `LANGUAGE CPYTHON` procedure: the CPython worker (the same code) |

MLE procedures write with `executeMany` / `execute_many`. The server runs with `mle.heap_max` 2 GB and
`mle.memory_max` 4 GB (as the earlier experiment; the defaults are 512 MB and 2 GB), `mle.sql_result_max`
1 GB, a 4 GB buffer pool and `innodb_flush_log_at_trx_commit` 1. Each measurement: one client (200
requests), and for `chatty` and `mmr500` 8 clients and for `wb200` 4 clients at once (200 each). Each
connection first warms up until the medians of two batches in a row agree within 3 % (400–2,000
requests; `--quick`: 150–400, then 100 requests, 50 each with several clients). Clients and the server share the machine.

Network: the clients run in a network namespace whose veth pair delays the server's packets by 1 ms
(`netem`; a round trip ~1.1 ms), as an application server on a LAN. Without `sudo -n` (or with
`--net loopback`) they use loopback, which hides what MLE saves in round trips; the results say which.

Results: `e2e.<case>.<client>.<variant>.p50_ms`, `.p95_ms`, `.qps` (one client) and `.c<N>_p50_ms`,
`.c<N>_p95_ms`, `.c<N>_qps` (N clients), with an `environment` block (CPU, memory, kernel, OS, governor,
commits and build types, MLE settings, network and its measured round trip, client versions), a
`checks` block (the same ids from every variant) and every measurement in `runs`.

## Requirements

- A **release** server build with MLE support and an MLE build (`RelWithDebInfo`) with the CPython
  worker (`MLE_CPYTHON=ON`): the data is generated by `LANGUAGE CPYTHON` procedures.
- **sudo -n** for `ip netns`, `tc` and `nsenter` (the 1 ms network); without it, loopback.
- **The JDK of the MLE build** (`MLE_JAVA_HOME` in its `CMakeCache.txt`, or `--java-home`) for the
  Java client.
- **Internet, once**: Connector/J 9.5.0 through Maven (`MLE_MAVEN` of the MLE build, or `mvn` in
  `PATH`: `dependency:copy`) and a venv with `mysql-connector-python==26.10.0 numpy==2.5.5` from PyPI.
  Offline: put `mysql-connector-j-9.5.0.jar` into `<work>/lib/`, and give `--python` an interpreter
  that has `mysql.connector` and `numpy` (or make `<work>/venv` yourself and touch `<work>/venv/.ready`).
- **Memory**: ~15 GB free for the full run (8 clients means 8 JVM workers, or 8 CPython workers, at
  once); clients stop when less than `--min-available-gib` (10) is available. **Disk**: ~3 GB in the
  work directory (data directory, venv).
- A quiet machine and the CPU governor `performance` for numbers worth comparing (the run warns).

## Run

```sh
perf/e2e/e2e.py --server ../BUILD-release --mle ../BUILD-mle-release --json e2e.json
```

The first run makes the data directory (a few minutes) in `<work>` (default `<MLE build>/perf-e2e`);
later runs reuse it while `setup.sql` and `client/Rerank.java` stay the same (otherwise delete
`<work>/data` and `<work>/setup.sha1`). The full run takes about 8 minutes on a 16-CPU laptop (`--wait-quiet` first waits for a load average below 1.5); `--quick` (fewer requests and
less warm-up, for checking the tool) ~5. `--cases chatty,wb200` or `--only 'python\.(app|cpython)'`
measure a part; `--no-concurrency` one client only. The server uses port 13994 (`--port`); the
namespace is `e2e<port>` with `10.213.94.0/24` (`--subnet`), removed at the end (`net.sh down e2e13994`
by hand after a crash).

Files: `e2e.py` (the driver), `setup.sql` (data and routines; the `LANGUAGE CPYTHON` copies are made
from the `LANGUAGE PYTHON` procedures), `client/E2E.java`, `client/Rerank.java` (the shared logic),
`client/SimdDot.java`, `client/e2e_client.py`, `net.sh` (the namespace; usable by hand).
